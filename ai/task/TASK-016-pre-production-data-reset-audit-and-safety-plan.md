## 4. Specific Operational & Security Audits

### A. Testimonial Classification & File Audit
- **Schema**: `testimonials` table contains `id`, `student_id` (FK `users` ON DELETE SET NULL), `course_level_id` (FK `course_levels` ON DELETE SET NULL), `name`, `photo`, `rating`, `testimonial`, `type`, `is_featured`, `is_active`.
- **Decision**: Testimonials are classified as **student-generated operational content** and are **DELETED IN BOTH RESET 1 AND RESET 2**.
- **Photo File Handling**: Testimonial photo files (`storage/app/public/testimonials/`) are operational upload files. DB records are deleted inside the transaction. Photo file cleanup can be run optionally post-commit.

### B. Student Session & Password Reset Token Filtering
- **Sessions**: The `sessions` table contains `user_id`. Before user deletion, Student User IDs are extracted: `$studentIds = DB::table('users')->where('role', 'student')->pluck('id')->toArray();`. Filtered deletion is executed: `DB::table('sessions')->whereIn('user_id', $studentIds)->delete();`. Admin & guest sessions are preserved.
- **Password Reset Tokens**: The `password_reset_tokens` table contains `email`. Before user deletion, Student emails are extracted: `$studentEmails = DB::table('users')->where('role', 'student')->pluck('email')->toArray();`. Filtered deletion is executed: `DB::table('password_reset_tokens')->whereIn('email', $studentEmails)->delete();`. Admin reset tokens are preserved.

### C. Certificate File Classification (Design Assets vs Generated Student PDFs)
- **PRESERVE (Design Assets)**:
  - Certificate template background images (`storage/app/public/certificate-templates/`)
  - Signatures (`storage/app/public/certificate-signatures/`)
  - Logos, stamps, decorative images
  - Default background templates (`public/images/certificates/certificate-default-background.jpg`)
- **DELETE OR QUARANTINE (Generated Student Certificates)**:
  - Generated student PDF files referenced in `certificates.certificate_file` (e.g. `storage/app/public/certificates/*.pdf`).
- **Post-Commit Cleanup Protocol**:
  1. Collect generated certificate file paths before DB deletion: `$generatedFiles = DB::table('certificates')->whereNotNull('certificate_file')->pluck('certificate_file')->toArray();`.
  2. Execute DB transaction.
  3. After DB commit succeeds, quarantine/delete generated certificate files. If file cleanup encounters an error, the DB reset remains validly committed and a warning log is generated.

### D. Course & Free Test Physical File Policy (Version 1)
- Course levels, materials, and posts contain file fields (`thumbnail_file`, `video_poster_file`, `file_path`).
- **Version 1 Decision**: Record deletion in Reset 1 purges database records, but **DOES NOT automatically delete physical uploaded Course & Free Test files** (`storage/app/public/materials/`, `course-thumbnails/`, etc.).
- **Rationale**: Prevents accidental file loss of master materials. Orphan file cleanup will be conducted in a separate dedicated task after DB reset stability is proven.
- Reset 2 maintains both DB records and physical files 100% intact.

### E. Queue & Maintenance Mode Preconditions
Before executing any reset command in the future:
1. Application enters Maintenance Mode (`php artisan down`).
2. Queue workers are stopped.
3. Pre-execution check inspects `jobs` and `job_batches`. If pending operational jobs exist, execution **ABORTS**.
4. Queue workers are restarted after post-reset verification completes.

### F. Cache Clearing Strategy
Post-reset cache clear (`php artisan cache:clear` / `optimize:clear`) will be executed **AFTER DB transaction commit**. Cache clear failure outputs a warning and does not trigger DB rollback.
